- P2 #the-browser-serves-the-bundle-not-the-source: After editing ParcelScene.ts I nearly tested the page as it stood. - P2 #i-invented-a-vocabulary-and-called-it-verification: I wrote 16 assertions in types that do not exist: file_min_bytes, runtime_behaviour, bundle_structure, gate, and file_not_contains, which is just the wrong name for file_lacks. - P3 #green-is-not-deployed: For two sessions the game was built, committed, pushed, and a green Deploy site tick appeared on every push. Nothing was deployed. The job checks for CLOUDFLARE_API_TOKEN, finds none, sets ready=false, skips Install/Bundle/Assemble/Deploy, and exits SUCCESS -- 12 to 17 seconds, green. The owner asked why he could not see his own character creation and the answer was a green tick that meant nothing. A skip that reports success is worse than a failure, because a failure gets fixed. - P4 #the-error-message-said-safe-while-it-locked-the-door: The lockout shipped with a reassuring sentence: Saving is not switched on yet. Your game is safe on this device. When a fallback path exists in the design (AuthGate has an offline branch and a comment saying the game is playable with no server), test that the CLASSIFIER can actually reach it. An unreachable fallback reads exactly like a working one in code review.

- P4 #my-verdict-string-said-still-blocked-about-a-working-deploy: Second time this session. I keyed the pass/fail on window.__realm, which main.ts sets ONLY on localhost -- by design, and documented in the boot snapshot I read at boot. So the successful production deploy reported STILL BLOCKED and I nearly relayed that. The signal I chose could not be true in the environment I was testing. Choose the observable from the environment under test, not from the one where the harness was written.

- P5 #it-was-drawn-as-a-button-and-was-not-one: Four bordered boxes across the top of the journal, the live one filled. That drawing is a promise: these are selectable. - P5 #a-label-computed-for-four-pages-and-printed-on-one: `turn` -- the page-turn key, read from the live keymap -- was computed on every redraw of every page and appeared in exactly one branch of the footer ternary. - P5 #i-wrote-a-test-that-could-not-fail: Third time this session, and the most instructive. To prove the tab strip does not also flip a help card, I pressed RIGHT then LEFT and asserted the card index was unchanged. It was -- and it would have been unchanged whether the bug existed or not, because 0 -> 1 -> 0 is 0. I caught it only because the symmetry looked too comfortable. A test whose pass condition survives the bug is worse than no test: it converts an open question into a false answer. Make the probe ASYMMETRIC and always include a control that proves the mechanism can move at all.

- P6 #the-cure-was-already-in-the-repo-with-a-comment-about-this-bug: Before writing a way to swallow the pending key edge I grepped for one, and found InputMap.drainEdges() - already implemented, already used by the Journal's rebind capture, and carrying a doc comment that explains the precise race I was about to re-derive: Phaser registers its window listener at boot, so a capture handler added later cannot win, whatever it does with stopImmediatePropagation. S114 paid for that knowledge and wrote it down. Creation was built afterwards with the same pattern and never called it. The lesson is not 'read the code' -- it is that a repo which writes its scars down is only protected if you search the scars before inventing a cure.

- P6 #my-test-data-was-invalid-and-it-looked-like-a-regression: After the ENTER fix the page would not advance at all, and the honest first reading was that I had over-corrected and broken forward navigation. Instrumenting canAdvance() instead of reasoning about it showed the truth in one call: the name `testp6` contains a digit, a character name forbids digits, and the refusal was correct. Two things fall out. Instrument before concluding, because 'my fix broke it' and 'my input was invalid' look identical from the outside. And the accident found a real bug -- the page pre-fills from the account username, which permits digits the character name rejects -- so anyone called daniel99 hits a silent refusal on their first play. A bad test can be better evidence than a good one if you find out WHY it failed.

- P6 #i-probed-the-two-i-could-not-do-before-saying-i-could-not: He said do all four. Two were his to unblock, and earlier this session I had already told him something was blocked on him that was not (the Cloudflare token was in the vault all along). - P7 #the-fix-that-made-it-pure-also-made-it-a-trap: Routing the name page through the keymap and deleting the literal `e.key === 'Enter'` was the clean version, and it introduced a soft-lock: a printable key must type on a page that takes a name, so a player who binds engage to a letter and clears its secondary would have had no way forward at all. Input.ts promises a primary EXISTS; it never promised the primary is non-printable, and I had read the first guarantee as if it were the second. Caught it by asking what the change REMOVED rather than what it added. The shipped version is additive -- ENTER used to be the only key that could act and is now the key that can always act.

- P7 #sanitise-the-offer-not-the-rule: Two validators disagreed -- an account name may hold digits, a character name may not -- and the page pre-filled one into the other. There were two directions: loosen the character-name rule, or stop proposing values it rejects. The rule is a deliberate 1601 constraint, so loosening it to make a prefill work would have let the convenience rewrite the design. Fixing the OFFER kept the rule intact and removed the trap. When two rules disagree, check which one is load-bearing before reconciling them.

- P7 #a-game-set-in-france-needs-its-accents-tested: I wrote a character filter and immediately tested Helene, Aime, Gaelle, Francois and Maitre d'Armes, because a sanitiser is exactly the code that silently eats an accent and nobody notices until a French player types their own name. My first probe DID report a false negative and the cause was my test string -- 'e' plus a combining accent is two code units and the length===1 gate rejects it, while the precomposed character a real keyboard sends is one. Test the input the machine actually produces, not the one you can type in a script.

## 2026-08-26 — Session S119: THE GAME GOT AN OWNER — accounts that follow you, 91 characters behind a palette seam, and the instrument that finally let a session look

- S119-1 #the-same-wrong-question-in-two-places-twice: `hasPosition` means "was the save ever WRITTEN", and `setAccount()` writes - so the instant anybody registered, a brand-new player looked exactly like a returning one. The resume window duly asked someone who had never moved whether to continue. I added `hasPlayed` (a real tile too, since a fresh save leaves the tile at -1), fixed ResumeGate, ran it, and it worked. Then a fresh browser refused to adopt the world it had just signed in to collect - because main.ts still said `hasPosition`, one call site over. I committed the SAME error twice in one hour, and the second time was AFTER writing the fix for the first. The repo has a standing law for exactly this ("two places deriving one number is a bug with a delay fuse") and knowing it did not help. What would have: when a getter turns out to answer the wrong question, grep every caller of it in the same edit, before running anything.

- S119-2 #erasing-is-not-a-local-act-once-there-is-an-account: "Start new game" called `restartWorld()`, wiped the save, booted a clean game, and looked perfect. Then I reloaded: main.ts saw a live token, pulled the account, found revision 1 still holding the old world, saw an empty local save - and adopted the dead world back. The erase had lasted one session. The server was already built for this (its own suite asserts "a restart is one ordinary write, and the revision goes UP"); the client just never published it. Generalises past restart: ANY local mutation that the server holds a copy of is provisional until it is pushed, and a feature that looks complete on one device is untested until the page is reloaded once.

- S119-3 #the-only-reason-i-found-any-of-this-was-that-he-said-see-it-work-first: Typecheck was clean, 3,125 client assertions passed, 9 guards passed, and 80 endpoint tests passed against a real Postgres - with all three of the above bugs live in the code. Every one of them was a WIRING fault between correct parts, which is exactly the class no unit test in this repo is positioned to see. His instruction was "we will build it and commit it and push it after we see it works on pc", and that instruction is the entire reason the feature is not broken. The lesson is not "write more tests"; it is that a chain assembled from proven links still has to be walked end to end, and reloading the page is part of walking it.

- S119-4 #adopting-a-world-should-not-adopt-a-login: `adoptRemote()` installs the downloaded save wholesale, and `account` - username, salt, password hash - is a field of the save. So signing in on a fresh device replaced its login with whichever one the uploading device happened to hold, or with null. The token masks it completely for that session; the player finds out the next time they are offline and the gate has nothing to check a password against. Found only because a hand-made test payload happened to carry `account: null`. Worth keeping as a shape: when a blob crosses a trust boundary, ask which of its fields belong to the WORLD and which belong to the PERSON - the two travel together in one JSON object and only one of them should be replaced. It also surfaced CF-S119-CREDENTIAL-IN-SAVE-BLOB: the hash is being stored twice, in two columns, for no reason.

- S119-5 #the-constraint-was-already-satisfied-before-i-invented-a-way-around-it: Five inks (outline, skin, hair, two attire colours) will not fit in a 3-colour sprite, and I was ready to solve it with two layered sprites or 90 generated files — both of which ship art through a guard that decodes exactly ONE hardcoded filename, so they would have passed dishonestly. The answer was to READ THE SEVEN EXISTING GRIDS: every hair and skin pixel was already at row <= 7 and every garment pixel at row >= 8. A 16x16 frame is four 8x8 regions, so the head band and the body band never share one and each needs only three inks. That is how GBC OBJ hardware assigned palettes. The constraint I was designing around had already been met by the art, years of sessions before anyone needed it. Generalises: before engineering past a limit, measure whether the existing work already clears it — and prefer the option that makes the GUARD stricter over the one that routes around it.

- S119-6 #the-type-system-caught-six-of-seven-and-the-seventh-was-the-dangerous-one: Adding `character` to SaveData made TypeScript reject seven sites, which is the migration convention working exactly as its comment promises. But the branch for v7 DID NOT EXIST, so a v7 save matched nothing and fell through to `return fresh()` — and every save in existence was v7, including the live one. The compiler cannot see a missing branch; it only checks the branches that are there. Worse, the suite would have passed: test 10's coverage loop was the literal `[1,2,3,4,5,6,BUILD_VERSION]`, which at v8 covers 1-6 and 8 and skips SEVEN. Two independent safety nets, both blind to the same hole, because both were enumerations rather than derivations. Now `Array.from({length: BUILD_VERSION})`. When a guard lists the cases it covers, the case it does not list is the one that ships.

- S119-7 #the-instrument-was-the-deliverable: I spent several exchanges concluding the creation flow was broken — the scene would not stop, the sprite would not change, the canvas came back one flat colour. All three readings were wrong and the code was correct. `document.hidden` was true, the frame counter was frozen at 2930, and TWO scene operations were sitting in a queue waiting for a frame that would never arrive. Because the bundle is ESM, Phaser never populates `Phaser.GAMES`, so there was no way to see any of that from the console. The fix that mattered was not to the game: it was three lines in main.ts exposing the game on localhost, after which every question answered itself in one call. This project's fifth and sixth boot rules ("LOOK AT IT", "now eight for eight") were both earned by unmeasured reads of rendered frames — and for 118 sessions nobody built the instrument those rules were asking for. When verification keeps being the expensive part, the instrument IS the priority.

- S119-8 #one-page-further-away-is-the-same-as-absent: I added the CHARACTER page between PLAY and ACCOUNT. RESTART lives on ACCOUNT, shipped and working, and he wrote back within minutes: "you still didnt add a restart game or whatever option im ESC joural." He was wrong about the feature and right about everything that matters — a destination that needs one more blind keypress to reach is a destination that does not exist. Two rules out of it: a NEW page goes on the END, because an existing destination never moves for something that just arrived; and a header showing "current + next" is honest and still hides the book, so it now shows every tab with the live one filled. Discoverability is not a polish task you schedule after the feature.

- S119-9 #a-duplicate-that-fails-loudly-is-a-copy-a-duplicate-that-falls-back-is-a-trap: The four option lists live in build-player.py AND Character.ts, and I shipped them that way without noticing what the failure mode WOULD be. `variantRow()` returns 0 for an appearance the sheet does not contain — a deliberate, defensible fallback for a save naming an option a later build removed. Combine that fallback with a drifting duplicate and you get the worst class of bug in this repo's taxonomy: no crash, no red guard, just every affected player quietly wearing the legacy traveller and it reading as a shrug. The fix was not to de-duplicate (you cannot import across the language boundary) but to make the copy CHECKED — the generator reads the TypeScript and refuses to build on a mismatch, negative-tested by injecting a sixth hair colour. The general rule: a graceful fallback and a duplicated source of truth are individually good and jointly a silent-failure machine. When you add the second, go back and look at the first.

- S119-10 #i-moved-my-own-assertion-one-priority-later: P3 asserted the exact line `ch.created === null ? 0 : variantRow(...)`. P4 — the coherence pass, correctly — rewrote it to route through `isCreated()`, and the gate went red on my own work from ninety minutes earlier. That is the fifth and sixth sighting of CF-S114-MCV-VERSION-ASSERTION-CLASS in ONE session: four historical needles, one of mine in P3, and one of mine again in P4 (a `file_lacks` on a literal my own explanatory comment quotes). The pattern is now unmistakable and it is not carelessness about needles — it is that I keep binding to the SHAPE OF TODAY'S CODE rather than to the claim. `variantRow(SHEET_VARIANTS, ch.appearance)` survives a refactor; the ternary around it does not. Before writing an assertion, ask what a CORRECT future change would do to it.

- S119-11 #the-count-that-named-no-true-number: rebuild-ci.yml carried a per-suite assertion tally — "evidence (12), scene-surface (13), box-layout (25), account-rules (58), save-migration (3,029)" — and it was wrong twice over: the numbers were stale AND they were paired with the wrong suites, so 12/13/25/58 were each somebody else's count. It read completely plausibly. A hand-maintained tally decays into fiction faster than a stale number does, because a shifted list still looks internally consistent. Kept it, corrected, for the one reason that justifies it: a count that DROPS is the only failure the runner cannot notice for itself. Everything else — "8 guards", said three times — was deleted rather than updated, because a number nothing verifies is a liability with a long fuse.
